# Design Discussion

Scope: BACKLOG rows 20–27 (GitHub issues #22–#29). Line references are from `research.md`
at commit 73835e4.

## Current State

**Persistence.** `PersistenceController.makeContainer` builds a plain `Schema(schemaTypes)`
with no `VersionedSchema` or `SchemaMigrationPlan` (`Sources/Persistence/PersistenceController.swift:6-17`).
`StoreBackup` copies the store files before open only when `CFBundleShortVersionString`
differs from the stored `lastRunAppVersion` (`Sources/Persistence/StoreBackup.swift:6,20`),
so a model change without a marketing-version bump produces no backup. Three version numbers
exist (marketing, archive `schemaVersion = 1`, unversioned SwiftData schema) and none is
linked to another.

**Import.** `DataArchiveActor.importData` decodes, then in replace mode runs `deleteAll()`,
then `upsertAll()`, then one `modelContext.save()` (`Sources/Services/Archive/DataArchive.swift:79-85`).
There is no `rollback()`, no transaction, and no snapshot. `StoreBackup` is never called
around an import. `SettingsView.runImport` maps every non-version error to "Import failed:
the file couldn't be read." (`Sources/Features/Settings/SettingsView.swift:110-111`); export
failures are silent (`:42`).

**Swallowed errors.** 69 lines in `Sources/` use `try?`; there is no `Logger`, `os_log`, or
`print` anywhere. `RootView.task` swallows the seed import (`Sources/RootView.swift:84`).
`SessionEditView` surfaces store-write failures but swallows every calendar and
`setEventIdentifier` call (`Sources/Features/Schedule/SessionEditView.swift:209-254`), and
a failed `update` overwrites the stored event identifier with nil (`:249-251`).
`SessionRunViewModel` has no error state and swallows 17 calls, including `delete` and
`setStatus` (`Sources/Features/Session/SessionRunViewModel.swift:51-133`).

**Notifications.** `requestAuthorization` folds errors into `false`, and the only caller
discards the Bool (`Sources/Services/ReminderCoordinator.swift:24`). `reschedule` removes
pending `sess-` requests then `try? center.add` without ever reading authorization status
(`Sources/Services/NotificationService.swift:72,85`). Notification status is read nowhere.

**Calendar.** `push` assigns `event.calendar = store.defaultCalendarForNewEvents` with no
nil check (`Sources/Services/CalendarService.swift:60`). `requestAccess` folds errors into
`false` (`:50`). `FakeCalendar` never throws or returns nil (`Tests/SessionRunViewModelTests.swift:5-23`).

**Packaging.** No `*.entitlements`, no `PrivacyInfo.xcprivacy`, no CI; `.github/` holds only
`CODEOWNERS`. `*.xcodeproj` is git-ignored and generated by XcodeGen (`.gitignore:11`).
README documents one simulator destination, "iPhone 17" (`README.md:24-29`).

**Tests.** Swift Testing, in-memory containers, two never-failing fakes. Zero references to
`EventKitCalendarService`, `LocalNotificationService`, `AppLock`, `ReportExporter`, seven
view models, every view, or replace-import into a non-empty store.

## Desired End State

1. The store opens through `SchemaV1` + `TrainMeMigrationPlan`; a future `SchemaV2` is a
   new enum plus one stage. The pre-open backup fires when the stored schema version
   identifier changes, not when the marketing version does.
2. A replace-import writes a `pre-import.json` snapshot first; if any later step throws,
   the context is rolled back, the snapshot is re-imported, and the user sees "Import failed,
   your previous data was restored." Merge-import gets the rollback but no snapshot.
3. Every path in `RootView.task`, `SessionEditView`, `SessionRunViewModel`, and
   `SettingsView` that can fail either surfaces a message or logs through `os.Logger`
   with a category. Calendar failures after a successful save show a non-blocking message
   and never clear a stored identifier on failure.
4. `reschedule` checks `notificationSettings().authorizationStatus` and adds only when
   authorized or provisional. `ReminderCoordinator` exposes the status; Settings shows a
   "Permissions" section with notification and calendar rows and an "Open Settings" link
   when denied.
5. `push` falls back to the first writable calendar when `defaultCalendarForNewEvents` is
   nil, and throws a typed `CalendarError.noWritableCalendar` when none exists.
6. `Sources/TrainMe.entitlements` (empty dict, wired via `CODE_SIGN_ENTITLEMENTS`),
   `Sources/PrivacyInfo.xcprivacy` declaring the `UserDefaults` required-reason API
   (CA92.1) and no tracking or collected data, and `.github/workflows/ci.yml` running
   `xcodegen generate` + `xcodebuild test` on a simulator with signing disabled.
7. Tests cover: replace into a non-empty store, failure mid-import restores the snapshot,
   `importArchive(url:)` with a missing or unreadable file, authorization-gated
   `reschedule`, calendar fallback and no-calendar error, `SessionRunViewModel` error
   state on failed delete/status/record, and `SessionEditView`'s calendar outcome logic.

**Verification.** `xcodebuild test` green locally and in CI. Manual on device: deny
notifications → Settings shows denied row and no alerts are scheduled; import a corrupt
archive in replace mode → data unchanged and message shown; delete the only calendar →
session saves with a calendar warning.

## Patterns to Follow

- **`save() async -> Bool` + `errorMessage`** on edit forms (`SessionEditView.swift:20,125-127,163`;
  `ClientEditViewModel.swift:15,49-55`). Extend this to `SessionRunViewModel` rather than
  inventing a new mechanism.
- **Protocol-per-service with default-argument injection** (`CalendarSyncing`
  `CalendarService.swift:34-44`; `NotificationScheduling` `NotificationService.swift:56-60`;
  `SessionRunViewModel.swift:31`). New seams (status provider, snapshot store) follow the
  same shape so tests inject fakes through initializers.
- **Typed error enum mapped to copy at the view** (`ArchiveError` `DataArchive.swift:8-11`
  → `SettingsView.swift:108-111`). Add cases rather than new enums where the domain matches;
  add `CalendarError` for the calendar domain.
- **Actor fakes in the test file that uses them** (`FakeCalendar`, `FakeNotifications`).
  Extend them with configurable failure modes (`shouldThrow`, `pushReturnsNil`).
- **Isolated `UserDefaults(suiteName:)` and temp directories** in tests
  (`Tests/StoreBackupTests.swift:5-10,19`).
- **`StoreBackup` records the version only after a successful copy** (`StoreBackup.swift:34`).
  Keep that ordering when the key changes.

**Do not follow:**
- `(try? ...) ?? []` as the only handling for a mutation. Acceptable for list loads
  that will be retried on next appear; not for `delete`, `setStatus`, `recordSet`,
  `updateNotes`, or any `setEventIdentifier`.
- `newId != existing.eventIdentifier` → write nil (`SessionEditView.swift:249-251`). A nil
  from failure must not be persisted.
- Folding thrown errors into `false` for authorization (`CalendarService.swift:50`,
  `NotificationService.swift:64`). Keep the Bool API but log the error and read the real
  status afterwards.
- One generic catch string for all import failures (`SettingsView.swift:110-111`).

## Design Decisions

1. **Schema versioning**: `enum SchemaV1: VersionedSchema` whose `models` equals today's
   `schemaTypes`, `versionIdentifier = Schema.Version(1, 0, 0)`, and
   `enum TrainMeMigrationPlan: SchemaMigrationPlan` with `schemas = [SchemaV1.self]`,
   `stages = []`. `makeContainer` passes `migrationPlan:`. The model classes stay where they
   are (not nested) so no call site changes. Rationale: zero-risk first step that makes the
   next schema change a one-stage addition.
2. **Backup trigger**: `StoreBackup` compares `SchemaV1.versionIdentifier.description`
   under a new key `lastRunSchemaVersion`; the old `lastRunAppVersion` key is read once for
   a one-time migration of the stored value, then removed. Backup directory becomes
   `pre-schema-<version>/`. Rationale: a backup exactly when a migration will run.
3. **Import safety = logical snapshot + rollback**: a new `SafeImporter` (plain struct,
   takes `any DataArchiving` and a snapshot URL) orchestrates: export → write snapshot →
   `importArchive` → on throw: `rollback()` inside the actor, then `importData(snapshot,
   .replace)`. Snapshot is deleted on success. `DataArchiveActor.importData` gains a
   `do/catch` that calls `modelContext.rollback()` and rethrows. Rationale: reuses the
   tested export/import path; avoids copying an open SQLite WAL; testable with a throwing
   fake `DataArchiving`.
4. **Error surfacing**: extend the existing pattern. `SessionRunViewModel` gains
   `errorMessage` and the run screen renders it; `delete()` returns Bool and the view
   dismisses only on `true`. `SessionEditView` gains `calendarWarning: String?` set when
   the session saved but calendar work failed; the sheet still dismisses and the warning is
   passed to `onSaved`'s caller via a brief `.alert`. `RootView` gains a one-shot
   `seedFailed` alert. `SettingsView` gets distinct copy for export failure, unreadable,
   newer version, decode failure, and "restored after failure". Rationale: six files, no
   new abstraction, matches what reviewers already know.
5. **Logging**: `enum Log { static let persistence, archive, calendar, notifications,
   ui: Logger }` with subsystem `com.madacgrav.trainme`. Every remaining `try?` on a
   mutation becomes `do/catch` that logs at `.error`; list loads may stay `try?` but log
   at `.debug` where cheap. Rationale: there is currently no way to diagnose a field
   failure.
6. **Notification gating**: `NotificationScheduling` gains
   `authorizationStatus() async -> UNAuthorizationStatus`. `reschedule` returns early
   unless `.authorized` or `.provisional` (still removing stale `sess-` requests).
   `ReminderCoordinator` stores `notificationStatus` as an observable property refreshed in
   `refresh()`. Rationale: stops silent add failures and gives Settings a value to show.
7. **Permission visibility**: new "Permissions" `Section` in `SettingsView` with two rows
   (Notifications, Calendar), each showing Allowed / Denied / Not asked and, when denied, a
   button opening `UIApplication.openSettingsURLString`. Calendar status comes from
   `CalendarSyncing.authorizationStatus()`, a new protocol requirement. Rationale: matches
   the backlog #17 direction; no new banner component.
8. **Calendar fallback**: in `push`, `store.defaultCalendarForNewEvents ??
   store.calendars(for: .event).first { $0.allowsContentModifications }`; if still nil,
   throw `CalendarError.noWritableCalendar`. `update` and `remove` unchanged. Rationale:
   the common nil case (no default set) is recoverable; the rare case is a real error.
9. **Packaging**: empty `Sources/TrainMe.entitlements` with `CODE_SIGN_ENTITLEMENTS` in
   `project.yml`; `Sources/PrivacyInfo.xcprivacy` with `NSPrivacyTracking = false`, empty
   collected-data array, and one accessed-API entry (`NSPrivacyAccessedAPICategoryUserDefaults`,
   reason `CA92.1`); both added to the app target's resources/settings. Rationale: App
   Store submission requires the manifest; the entitlements file gives capabilities a home.
10. **CI**: `.github/workflows/ci.yml`, triggers `push` to `main` and `pull_request`, runs on
    `macos-26` (Xcode 26), steps: checkout, `brew install xcodegen`, `xcodegen generate`,
    `xcodebuild -scheme TrainMe -destination 'platform=iOS Simulator,name=iPhone 17'
    CODE_SIGNING_ALLOWED=NO test`. Rationale: matches README verbatim; no UI target.
11. **Testing the services**: do not drive real `EKEventStore` or
    `UNUserNotificationCenter` in unit tests. Test the gating logic by extending the fakes
    and by unit-testing `SafeImporter` with a throwing `DataArchiving` fake. Test the
    `SessionEditView` calendar-outcome logic by extracting it into a pure function
    (`resolveEventIdentifier(existing:result:) -> String??` style) with its own tests.

## What We're NOT Doing

- No `SchemaV2` or any model change; `SchemaV1` mirrors today's models exactly.
- No physical store-file snapshot before import; `StoreBackup` stays launch-only.
- No shared toast/banner component; no changes to the export-reminder banner.
- No UI test target; no device builds or archive steps in CI.
- No settings toggles for lock, calendar default, or lead times (backlog #17 proper).
- No series edit/cancel calendar work (backlog #7) and no change to `SessionRunViewModel`
  skipping calendar removal for series sessions.
- No re-prompt UI for Face ID; `AppLock` tests are limited to what `LAContext` injection
  allows and may be deferred if that seam proves invasive.
- No change to list-loading `(try? ...) ?? []` beyond adding debug logging.
- No reworking of `RecoveryView` or adding import to it.

## Open Risks

- **SwiftData `delete(model:)` semantics.** If it executes against the store immediately
  rather than staging, `rollback()` will not undo it and the snapshot re-import carries
  the full recovery load. The snapshot path must therefore be tested as the primary
  mechanism, not a fallback.
- **Adopting `VersionedSchema` on an existing unversioned store.** SwiftData should treat
  a matching `SchemaV1` as current with no migration, but this must be verified on a
  device with real data before merging (export first).
- **`macos-26` runner availability and Xcode 26 default.** If the image is not yet
  available or Xcode 26 is not the default, the workflow needs `xcode-select` or
  `DEVELOPER_DIR` pinning, which the README already documents for local use.
- **Simulator name drift.** "iPhone 17" must exist on the runner image; the workflow
  should fail with a clear message rather than hang if it does not.
- **`UNUserNotificationCenter` in tests.** Any test that constructs
  `LocalNotificationService` directly will touch the real center; keep service tests
  behind the protocol fakes.
- **Snapshot size and privacy.** `pre-import.json` lives in Application Support with
  `.completeFileProtection`; it must be deleted on success and on next launch if left over.
